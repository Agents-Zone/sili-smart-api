### 1.3 创建背景

> [修改] 基线创建背景（对话原文落库需求）详见基线 §1.3，本次变更补充以下背景。

外部 AI 分析平台经集成密钥拉取对话记录后，会话列表与详情里携带了 `user_id`、`username`、`token_name` 维度。平台需要一份独立的用户名与 API key 名称目录来解析、展示和映射这些维度。现有 `/api/user/self` 走 `middleware.UserAuth()` 登录态认证，外部平台无法使用，且其返回的是当前登录用户的完整信息。本次变更在集成密钥套件中新增一个精简字典接口，仅返回用户名与 API key 名称，不泄露 key 明文、配额、邮箱等敏感字段；`/api/user/self` 及其登录态认证保持原样，不做改动。

### 1.4 技术栈

> **[无变化]** 与基线一致：Go 1.22+ / Gin / GORM v2 / ClickHouse / go-redis / gopool / i18n。本次新增接口复用主库 users/tokens 表（GORM 只读查询），不引入新依赖。

#### 用户信息字典结构

```go
package model

// ConversationToken 用户名下单个 API key 的精简信息，仅名称维度。
type ConversationToken struct {
    TokenID   int    `json:"token_id"`
    TokenName string `json:"token_name"`
}

// ConversationUserSummary 用户信息字典聚合行，按用户聚合。
type ConversationUserSummary struct {
    UserID   int                 `json:"user_id"`
    Username string              `json:"username"`
    Tokens   []ConversationToken `json:"tokens"`
}

// ConversationUserQueryParams 用户信息字典过滤维度。
type ConversationUserQueryParams struct {
    Username  string
    TokenName string
}
```

分页响应的 `data` 为 `{ page, page_size, total, items }`，`items` 为 `[]ConversationUserSummary`，按 `user_id` 升序；每个用户的 `tokens` 数组按 `token_id` 升序。

### 2.4 能力详细说明

#### 能力8：用户信息字典查询（ListConversationUsers）

**描述**：面向外部 AI 分析平台的用户名与 API key 名称字典查询接口，经集成密钥认证，按用户聚合返回启用状态用户的 `username` 与名下启用 token 的 `token_name`，不含 key 明文与配额等敏感字段。

**接口定义**：
```go
package model

// ListConversationUsers 按用户聚合分页返回启用状态用户的 username 与名下启用 token_name。
// users.status=1 且未软删除；tokens.status=1 且未软删除（GORM 自动过滤 DeletedAt）。
// username 模糊过滤用户；token_name 模糊过滤用户名下的 token，仅保留至少含一个匹配 token 的用户。
// 按 user_id 升序分页。返回 ([]ConversationUserSummary, int64, error)，
// int64 为满足条件的用户总数（controller 分页 PageInfo 需要）。
func ListConversationUsers(params *ConversationUserQueryParams, page, pageSize int) ([]ConversationUserSummary, int64, error)
```

```go
package controller

// ListConversationUsers 返回用户信息字典，按用户聚合，
// 仅 user_id/username 与名下 token_id/token_name，集成密钥认证。
func ListConversationUsers(c *gin.Context)
```

**调用示例**：
```go
// router/api-router.go，集成密钥路由组新增一行（完整代码见 §4.2）：
//   conversationLogRoute.GET("/users", controller.ListConversationUsers) // [新增]
// 与 /:session_key 同层；Gin v1.9.1 静态路由优先匹配，
// session_key 由 common.NewRequestId() 生成，值域不含裸字符串 "users"，无碰撞风险。
```

```bash
# 用户信息字典（按用户聚合，可按 username/token_name 过滤）
curl -H "Authorization: Bearer $CONVERSATION_LOG_INTEGRATION_KEY" \
  'http://localhost:3000/api/conversation-log/users?username=user&page_size=20'
```

**响应示例**：
```json
{
  "success": true,
  "message": "",
  "data": {
    "page": 1,
    "page_size": 20,
    "total": 2,
    "items": [
      {
        "user_id": 2,
        "username": "user1",
        "tokens": [
          { "token_id": 10, "token_name": "my-token" },
          { "token_id": 11, "token_name": "prod-key" }
        ]
      },
      {
        "user_id": 3,
        "username": "user2",
        "tokens": [
          { "token_id": 12, "token_name": "test" }
        ]
      }
    ]
  }
}
```

**注意事项**：
- 数据来源为主库 users/tokens 表（GORM 只读查询，三库兼容），非 ClickHouse 日志库；不读写 `conversation_turns`，与基线「存储仅 ClickHouse」约束不冲突（该约束针对 `conversation_turns` 的写入存储）。
- 仅返回启用状态：`users.status=1`、`tokens.status=1`，软删除记录由 GORM 自动过滤。
- 字段最小化：响应仅含 `user_id`/`username` 与 `token_id`/`token_name`，敏感字段（key 明文、密码、邮箱、配额用量等）一律不进入响应，完整清单见 §3.2 安全要求。
- 认证复用 `middleware.ConversationLogAuth()`，错误码与会话列表/详情一致：未配置密钥 403 `CONVERSATION_LOG_KEY_NOT_CONFIGURED`，密钥缺失/错误 401 `CONVERSATION_LOG_INVALID_KEY`。
- 查询类异常返回与会话列表/详情一致：查询参数非法（`page` 为负、时间范围倒置等）返回 400；无满足条件用户返回 200 与空 `items`（`total=0`）；数据库内部错误返回 500，错误信息经 go-i18n 国际化。`page_size` 越界按上限 100 截断，不报错。
- 路由与 `/:session_key` 同层共存：Gin v1.9.1 静态路由优先匹配，`/users` 命中静态段，其余路径命中 `:session_key`；`session_key` 由 `common.NewRequestId()` 生成，值域不含裸字符串 `users`，无碰撞风险。项目 `adminRoute` 下 `/search` 与 `/:id` 共存已是先例。
- 分页以用户为单位（`common.GetPageQuery`，`page_size` 上限 100）；`token_name` 过滤只作用于用户名下的 token 维度：未指定时返回该用户全部启用 token，指定时只返回匹配 token，并仅保留至少有一个匹配 token 的用户。用户与启用 token 采用 LEFT JOIN：只要 `users.status=1` 即返回该用户，名下无启用 token 时 `tokens` 为空数组（便于外部平台解析历史对话中残留的 `user_id`/`username` 维度）。
- 名称可能随用户/令牌编辑变更，不做缓存，每次查主库；查询开销与用户/token 规模成正比，外部平台按需低频调用。

### 3.1 数据库兼容性（补充）

> [修改] 基线 `conversation_turns` 仅落 ClickHouse 的约束不变；本次新增接口读取主库 users/tokens 表，补充如下。

| 依赖 | 版本要求 | 说明 |

| SQLite / MySQL / PostgreSQL | 项目支持版本 | 用户信息字典接口读取主库 `users`、`tokens` 表，使用 GORM 方法查询（`Where`/`Find`/分页），三库均须兼容。仅查启用状态（`status=1`），软删除由 GORM 自动过滤，无方言专用 SQL、无 `ALTER COLUMN` |

### 3.2 安全要求（补充）

> [修改] 基线安全要求（集成密钥唯一屏障、token 明文不落库等）不变；本次新增接口补充字段最小化披露约束。

| 安全项 | 要求 | 实现方式 |
|--------|------|---------|
| 字段最小化 | 仅返回名称维度 | 响应仅含 `user_id`/`username`/`token_id`/`token_name`；token 的 `Key`（API key 明文）、user 的 `Password`/`Email`/`AccessToken`、配额与用量字段一律不进入响应 |

> **[无变化]** 基线 §3.1 硬约束（最小侵入）、§3.2 性能、§3.3 兼容性中的协议与路径白名单、§3.4 安全（基线部分）、§3.5 可靠性、§3.6 已知局限：均不涉及用户信息字典接口，详见基线。

### 5.1 用户信息字典接口测试

| 测试场景 | 测试方法 | 预期结果 |
|---------|---------|---------|
| 按用户聚合 | 造 1 用户 2 启用 token，查 `/users` | 返回 1 行，`tokens` 含 2 项，`token_id`/`token_name` 正确 |
| 仅启用状态 | 造启用 + 禁用用户/令牌各若干 | 仅启用用户与启用 token 出现，禁用与软删除记录排除 |
| 启用用户无启用 token | 造 1 启用用户，其所有 token 均禁用或软删除 | 该用户仍返回（LEFT JOIN 语义，`users.status=1` 即入结果），`tokens` 为空数组 |
| username 过滤 | `?username=user` | 仅返回 username 模糊匹配的用户 |
| token_name 过滤 | `?token_name=prod` | 仅返回名下含匹配 token 的用户，且 `tokens` 只含匹配项 |
| 分页 | `page_size` 越界与正常 | 越界按上限 100 截断；`total` 为满足条件用户总数；按 `user_id` 升序 |
| 集成密钥认证 | 不带/错带/正确带 Bearer | 无密钥或错误 → 401 `CONVERSATION_LOG_INVALID_KEY`；服务端未配密钥 → 403 `CONVERSATION_LOG_KEY_NOT_CONFIGURED`；正确 → 200 |
| 路由共存 | 请求 `/users` 与 `/<真实 session_key>` | `/users` 命中 ListConversationUsers，session_key 路径命中 GetConversation，互不串扰 |
| 字段最小化 | 查任意用户 | 响应不含 `key`/`password`/`email`/`quota` 等敏感字段 |
