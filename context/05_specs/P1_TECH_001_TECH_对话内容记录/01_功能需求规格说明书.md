# 技术组件规格说明书

## 1. 概述

### 1.1 组件名称
对话内容记录（ConversationLog）

### 1.2 组件描述
在 AI 网关中转链路上以最小侵入方式捕获请求与响应明文，按会话聚合入库，向管理员提供完整多轮对话查询能力的技术组件。它只新增一个挂于 relay 路由分组的 gin middleware 与一套查询 API，不修改任何中转 handler、relay 流程与 RelayInfo。

### 1.3 创建背景
现有 `logs` 表只记计费摘要和 token 数，不落库对话原文。当需要审计、问题回溯或按会话还原完整多轮对话时，缺少数据来源。需求文档「对话内容记录功能（按会话聚合）— 最小侵入版」明确了硬约束：原有代码只动 1~2 处，不碰任何中转 handler、不改 relay 流程、不改 RelayInfo；全部能力（捕获、解析、会话识别、存储、查询、开关、建表）都通过新建文件实现。组件在满足该约束的前提下，以 middleware 拦截 + 开关/建表内化的策略，实现对话明文捕获、协议解析、启发式会话识别、日志库存储与管理员查询的完整闭环。

本组件是通用技术能力：捕获、解析、会话聚合、查询的机制不绑定具体业务，可复用于网关内任何需要按会话还原对话的场景，不归属单一业务模块。

### 1.4 技术栈
| 技术 | 版本 | 用途 |
|------|------|------|
| Go | 1.22+ | 后端实现语言 |
| Gin | 当前项目版本 | HTTP 框架，middleware 与路由挂载 |
| GORM v2 | 当前项目版本 | 数据模型与数据库访问 |
| ClickHouse | 项目支持版本 | 存储仅走 ClickHouse 日志库（`LOG_SQL_DSN`），开启功能时必须配置 |

| i18n（go-i18n） | 当前项目版本 | 后端错误信息国际化 |

## 2. 组件接口

### 2.1 能力清单

| 序号 | 能力名称 | 能力类型 | 说明 |
|------|---------|---------|------|
| 1 | 对话捕获（ConversationLog middleware） | 基础 | 拦截 relay 文本对话请求，捕获请求体与完整响应字节 |
| 2 | 协议消息解析（parseRequestMessages / parseAssistantContent） | 基础 | 将 OpenAI/Claude/Gemini 三协议 messages 归一化为 `[]MsgPart{role,kind,text}`，区分 text/tool_use/tool_result |
| 3 | 用量解析（parseUsage） | 基础 | 从响应 usage 解析 prompt/completion tokens，不查 logs、不做计费运算 |
| 4 | 启发式会话识别（prefixHash + 会话缓存） | 基础 | 按 token_id + 内容前缀哈希识别会话归属，Redis 跨实例共享 |
| 5 | 会话持久化（migrateClickHouseLogDB 建表 / RecordConversationTurn） | 基础 | 启动迁移建表与 TTL 同步（与 logs 同路径），按轮次增量写库，一行一轮 |
| 6 | 会话查询（ListConversations / GetConversationTurns / MergeConversation） | 高级 | 按 session_key 聚合列表与逐轮详情，查询侧拼接完整对话 |
| 7 | 管理员查询 API（GET /api/conversation/） | 高级 | 面向管理后台的会话列表与详情 REST 接口 |

> **能力类型说明**：基础=核心必需能力 | 高级=增强型能力 | 扩展=可选能力

#### REST API（仅管理员）

| 方法 | 路径 | 返回 | 说明 |
|------|------|------|------|
| GET | `/api/conversation/` | 会话列表 | 按 session_key 聚合分页，仅聚合字段，不含消息内容 |
| GET | `/api/conversation/:session_key` | 会话详情 | `{session, messages, turns}`；`turns` 为逐轮元数据，完整对话序列统一由 `messages` 返回 |

**会话列表查询参数**：`token_name`/`username`/`model_name`/`start_timestamp`/`end_timestamp`（对齐 logs 查询参数）、分页 `p`/`page_size`（`common.GetPageQuery`）。时间直接过滤轮次 `created_at`（时间窗口内有过轮次的会话），列表按末轮时间倒序返回。

**会话详情返回结构**：
- `session`：聚合元数据（token_name、username、user_id、model_name、首末轮时间、轮数）
- `turns`：逐轮元数据（id/created_at/request_id/turn_kind/truncated），不含每轮消息内容，避免与汇聚的 `messages` 重复
- `messages`：当前返回 turns 内按 `created_at, request_id` 升序逐行 append 得到的完整 `[]MsgPart` 序列，是详情响应的唯一消息内容来源

长会话详情分页单独解析 `p`/`page_size`，不走 `common.GetPageQuery` 的 100 上限，`page_size` 允许最大 200；单响应上限 200 轮，超限截断并置 `truncated` 提示。

### 2.4 能力详细说明

#### 能力1：对话捕获（ConversationLog middleware）

**描述**：拦截 relay 文本对话路径，零开销开关控制，捕获请求体与完整响应字节，异步编排入库。关闭时直接 `c.Next()` 不包装 writer、不读 Body。

**接口定义**：
```go
package middleware

// ConversationLog 返回一个挂载在 relay 路由分组上的 gin middleware。
// 读取 CONVERSATION_LOG_ENABLED：关时直接 c.Next() 零开销；开时先按
// 路径白名单过滤（见 §3.3），命中才继续捕获，随后 gopool.Go 调
// service.RecordConversation，闭包只捕获纯值。
func ConversationLog() gin.HandlerFunc

// conversationResponseWriter 照抄 auditResponseWriter 的包装模式：
// 嵌入 gin.ResponseWriter，body *bytes.Buffer，maxSize 上限（首版 256KB）。
type conversationResponseWriter struct {
    gin.ResponseWriter
    body    *bytes.Buffer
    maxSize int
}
```

**service 层输入契约 `ConversationInput`**（middleware 异步闭包捕获的纯值快照，经 `gopool.Go` 传给 `service.RecordConversation`，见 §2.4 能力1 注意事项与 §4.2）：

```go
package service

// ConversationInput 是一次请求/响应的纯值快照，middleware 闭包在 c.Next() 后的
// 同步段捕获，经 gopool.Go 传入 RecordConversation。字段全部来自这一次请求/响应
// 或 context，不查 logs、不做计费运算。
type ConversationInput struct {
    SessionKey        string
    RequestID         string
    CreatedAt         int64
    Messages          []MsgPart
    TurnKind          string
    Truncated         int64
    ModelName         string
    ChannelID         int
    TokenID           int
    TokenName         string
    UserID            int
    Username          string
    Group             string
    IP                string
    UseTime           int64
    IsStream          bool
    UpstreamRequestID string
    PromptTokens      int
    CompletionTokens  int
    // 解析输入（middleware 同步段捕获的原始数据）
    Path            string
    RawRequestBody  []byte
    RawResponseBody []byte
}
```

**调用示例**：
挂载方式见 §2.2 middleware 挂载点（权威定义）：在 `router/relay-router.go` 的 `httpRouter` 与 `relayGeminiRouter` 上注册 `middleware.ConversationLog()`，注册在 `Distribute()` 之前作为外层。

**注意事项**：
- 取值时机必须在 `c.Next()` 后的同步段：请求体经 `storage.Bytes()` 取出后立即 `bytes.Clone`（`memoryStorage.Bytes()` 返回内部 slice 引用，且 `BodyStorageCleanup` 请求结束即 Close storage），响应体从自定义 writer 拷出，context 字段拷成纯标量，范式参照 `finishAdminAudit`（middleware/audit.go）。
- 流式与非流式响应均经 `c.Writer`（全仓无 Hijack，realtime 走 websocket 不经 `c.Writer`），包装不漏数据。
- `ChannelId` 由 `Distribute` 在自身 `c.Next()` 之前经 `SetupContextForSelectedChannel` 写入，故本 middleware 无论作为 Distribute 外层或内层，均能在自身 `c.Next()` 后读到。
- 建表与 TTL 同步由启动迁移 `migrateClickHouseLogDB` 负责（与 logs 同路径同时机），middleware 只做捕获，不在请求路径建表。

#### 能力2：协议消息解析（parseRequestMessages / parseAssistantContent）

**描述**：把 OpenAI/Claude/Gemini 三协议的请求 messages 与响应 assistant 输出归一化成 `[]MsgPart`。请求侧把真人输入与工具结果分开，响应侧把工具调用与文本分开。

**接口定义**：
```go
package service

// parseRequestMessages 按 path 定协议，把请求体 messages 归一化成 []MsgPart。
// OpenAI 的 role=tool 标 Kind=tool_result；Claude 包在 user role content 里的
// tool_result block 也标 Kind=tool_result；首轮全部 request 侧消息按请求原序作为首轮增量。
func parseRequestMessages(path string, body []byte) ([]MsgPart, error)

// parseAssistantContent 输出同结构 []MsgPart：text 段标 Kind=text，
// function_call/tool_use 标 Kind=tool_use（text 存工具名与入参的紧凑表示）。
// 非流式解析 JSON，走 common.Unmarshal；流式逐行扫描 SSE，按协议与载荷内
// type 字段分派增量位置。
func parseAssistantContent(path string, isStream bool, respBytes []byte) []MsgPart
```

**调用示例**：
```go
// service/conversation.go 内按 path 分支，三协议增量字段位置各不相同：
// OpenAI chat/completions 载荷无 type，text 取 choices[].delta.content/reasoning_content，
//   工具取 choices[].delta.tool_calls[].function.name/arguments
// OpenAI Responses 按事件类型走，text 取 response.output_text.delta，
//   工具取 response.output_item.added(function_call) 与 response.function_call_arguments.delta
// Claude 按 content_block_delta 分派，工具参数增量在 delta.type="input_json_delta" 的 partial_json
```

**注意事项**：
- 流式解析机械上跳过 `event:` 行、剥 `data:` 前缀（relay/helper/stream_scanner.go 同法）。
- 三种协议增量字段位置各不相同，解析器必须按 path 分支。
- 失败/错误响应（上游 4xx/5xx）同样入库：request 侧消息按请求体解析保留，assistant 侧按响应体实际内容解析（错误 JSON 无消息体时记空）。

#### 能力3：用量解析（parseUsage）

**描述**：从响应 usage 解析 prompt/completion tokens。本表 token 的唯一来源，不查 logs、不做任何计费运算。

**接口定义**：
```go
package service

// parseUsage 从响应字节解析 prompt/completion tokens。
// OpenAI 非流式取顶层 usage；流式取末个带 usage 的 chunk（依赖客户端
// stream_options.include_usage，未带记 0）；Responses 流式取 response.completed
// 事件的 Response.Usage；Claude 非流式取顶层 usage，流式须合并 message_start
// 与 message_delta 两处 usage；Gemini 取 usageMetadata，流式下取末个带
// usageMetadata 的 chunk。
func parseUsage(path string, isStream bool, respBytes []byte) (promptTokens, completionTokens int)
```

**注意事项**：
- 流式未带 `include_usage` 时 `completion_tokens` 记 0，属协议限制而非 bug，查询侧对 `completion_tokens=0` 的流式记录知情。
- 只读响应字节，不碰 handler、不做任何计费运算。`LogConsumeEnabled=false`（logs 关闭）不影响本表记录。

#### 能力4：启发式会话识别（prefixHash + 会话缓存）

**描述**：按 `token_id` 分桶 + 内容前缀哈希识别会话归属。客户端不可改、协议无状态，故采用启发式识别。会话指纹到 sessionKey 的短期映射走 Redis，多实例共享。

**接口定义**：
```go
package service

// prefixHash 按 token_id 分桶计算本轮 request 侧内容的前缀指纹。
// 对组合后的本轮 request 侧消息文本取前 64 字符计算指纹。
// 全量内容强校验的 fullHash 首版不做，指纹冲突即误并按「启发式会话边界」接受。
func prefixHash(tokenID int, requestParts []MsgPart) string

// 私有 helper，直连 common.RDB，不动 common/redis.go（维持改动 1~2 处硬约束）：
// - RedisSetNX 原子抢占：SET NX EX 是原子的，可用作抢占；普通 RedisSet 不能当锁用
// - RedisExpire 命中即滚动续期 TTL，活跃会话不断链
func redisSetNX(key, value string, ttl time.Duration) (bool, error)
func redisExpire(key string, ttl time.Duration) error
```

**调用示例**：
```go
// 键形如 conv:session:{token_id}:{prefixHash}，TTL 30min
ok, _ := redisSetNX("conv:session:"+strconv.Itoa(tokenID)+":"+hash, sessionKey, 30*time.Minute)
if !ok {
    sessionKey, _ = common.RedisGet(key) // 失败者重读已存在的 sessionKey
}
```

**注意事项**：
- 命中复用 `sessionKey` 并滚动续期 TTL（`RedisExpire`）；未命中生成新 sessionKey，`RedisSetNX` 原子抢占，胜出者用自己的 sessionKey，失败者 `RedisGet` 重读，消除首请求并发劈会话窗口。
- `!common.RedisEnabled` 时退化为进程内 map，并 `common.SysError` 标注单实例模式。
- 本轮 request 侧增量按内容类型组合：纯文本轮为末条 `role=user` 消息；含工具结果轮为全部 tool_result 消息 + 末条 `role=user` 消息（按真实时序，tool_result 在前）；新建会话首轮为全部 user 侧消息（按请求原序）。
- 会话状态落在 Redis 后，网关重启不再断链（TTL 内续得上），多副本跨实例能续上同一会话。

#### 能力5：会话持久化（migrateClickHouseLogDB 建表 / RecordConversationTurn）

**描述**：启动迁移建表与 TTL 同步（与 logs 同路径同时机），按轮次增量写库。一行一轮，`messages` 单列存本轮完整消息序列，写入路径不维护 `turn_seq` 自增，轮次顺序交由查询侧排序。

**接口定义**：
```go
package model

// conversationTurnCreateTableSQL 生成 ClickHouse 建表 DDL，由 migrateClickHouseLogDB
// 启动迁移调用（与 logs 同函数同时机）：id Int64 DEFAULT 0（CH 无自增）、ENGINE=MergeTree()、
// PARTITION BY toYYYYMM(toDateTime(created_at))、ORDER BY (session_key, created_at, request_id)；
// TTL 天数由调用方传入（conversation_turns 读 LOG_CONVERSATION_CLICKHOUSE_TTL_DAYS，与 logs 各自独立），建表后经 syncClickHouseTTL 动态 MODIFY TTL 对齐配置。
func conversationTurnCreateTableSQL(ttlDays int) string

// RecordConversationTurn 写入一轮会话记录。
func RecordConversationTurn(turn *ConversationTurn) error

// ListConversations 聚合分页：以 session_key 为聚合键，GROUP BY 每会话一行，
// 聚合首末轮时间与轮数；过滤维度对齐 logs 查询参数（token_name/username/model_name/
// start_timestamp/end_timestamp）；按末轮时间倒序。
// 返回 ([]ConversationSummary, int64, error)，int64 为聚合会话总数（分页必需，
// controller 的 PageInfo 需要）。
func ListConversations(params *ConversationQueryParams, page, pageSize int) ([]ConversationSummary, int64, error)

// GetConversationTurns 按 created_at, request_id 升序取行，同时返回每行 messages 列解码结果。
func GetConversationTurns(sessionKey string) ([]ConversationTurn, error)
```

**调用示例**：
```go
// service.RecordConversation 内组装 ConversationTurn，一次写库：
// 所有字段均来自这一次请求/响应或 context，无查 logs、无计费运算、无二次更新、无 sleep。
turn := &model.ConversationTurn{
    SessionKey:        sessionKey,
    RequestID:         requestID,
    Messages:          joinedParts, // 请求侧在前、响应侧在后，物理时序即真实顺序
    TurnKind:          turnKind,
    ModelName:         modelName,
    ChannelID:         channelID,
    // ... 其余维度字段
}
_ = model.RecordConversationTurn(turn)
```

**注意事项**：
- `group` 是保留字，列名按 `logGroupCol` 方言约定处理：ClickHouse 用反引号。
- `token_name`/`username` 从 context 直接取（middleware/auth.go 已写入 `token_name`，`username` 用 `c.GetString("username")`）；token 明文 key（`ContextKeyTokenKey`）不落库，管理员按名称查询，与 logs 表惯例一致。
- 跨库聚合约束：SELECT 中 `session_key` 之外的维度列必须用聚合函数包裹（ClickHouse 用 `any()`），禁止裸返回非聚合列。首末轮时间与轮数是时间窗口内轮次的统计，非会话全量统计。
- ClickHouse 方言分支仿 `clickHouseLogOrder`。

#### 能力6：会话查询（ListConversations / GetConversationTurns / MergeConversation）

**描述**：查询侧负责轮次排序与对话拼接，返回逐轮元数据与完整扁平序列。

**接口定义**：
```go
package service

// MergeConversation 按 created_at, request_id 升序逐行 append 每行 messages 列，
// 得到完整 []MsgPart 序列。turn_kind/truncated 作为逐轮元数据随行返回。
func MergeConversation(turns []model.ConversationTurn) []MsgPart
```

**注意事项**：
- 轮次顺序完全交给查询侧：查询侧按 `ORDER BY created_at, request_id` 取行，ClickHouse 建表 `ORDER BY (session_key, created_at, request_id)`。写入路径无需维护 `turn_seq` 自增，规避「读 ClickHouse 当前最大值加一」的竞态与每次写入的额外查询。
- 秒级 `created_at` 无法稳定区分同一会话同一秒内并发的多轮，双键排序是必要设计。

#### 能力7：管理员查询 API（GET /api/conversation/）

**描述**：面向管理后台的会话列表与详情 REST 接口，仅管理员可访问。

**接口定义**：
```go
package controller

// ListConversations 返回会话列表，仅聚合字段（session_key、首末轮时间、轮数、
// token_name、username、user_id、model_name），不含消息内容。
func ListConversations(c *gin.Context)

// GetConversation 返回 {session, messages, turns}。session 为聚合元数据；
// turns 为逐轮元数据（id/created_at/request_id/turn_kind/truncated，不含每轮消息内容，
// 避免与 messages 重复）；messages 为按 created_at, request_id 升序 append 得到的完整
// []MsgPart 序列，是详情响应的唯一消息内容来源。长会话详情分页单独解析
// p/page_size（不走 GetPageQuery 的 100 上限，允许最大 200），单响应上限
// 200 轮，超限截断并置 truncated 提示。
func GetConversation(c *gin.Context)
```

**调用示例**：
```go
// router/api-router.go，管理员路由组注册
router.GET("/api/conversation/", controller.ListConversations)
router.GET("/api/conversation/:session_key", controller.GetConversation)
```

**注意事项**：
- 查询参数与 logs 对齐：`token_name`/`username`/`model_name`/`start_timestamp`/`end_timestamp`。会话列表分页沿用 `common.GetPageQuery`（`page_size` 上限 100）；会话详情分页单独解析，不走 `common.GetPageQuery` 的 100 上限，`page_size` 允许最大 200。
- 不回传整表维度字段（ip/channel_id/token_id/use_time 等不进入详情响应）。
- 异常返回：session_key 无记录时返回 404；查询参数非法（分页越界、时间范围倒置等）返回 400；其余内部错误返回 500，错误信息经 go-i18n 国际化。

## 3. 技术约束

### 3.1 硬约束（最小侵入）

| 约束 | 要求 | 说明 |
|------|------|------|
| 现有代码改动 | 仅 1~2 处 | 只动 `router/relay-router.go`（两处 middleware 挂载）与 `router/api-router.go`（查询入口，可选）；relay/channel/ 下所有 handler、`relay_info.go`、`text_quota.go`、`constants.go`、`option.go`、`main.go` 一律不动 |
| 功能逻辑承载 | 全部新建文件 | middleware/conversation_log.go、service/conversation.go、model/conversation.go、controller/conversation.go |
| 不碰中转流程 | 禁止 | 不修改任何中转 handler、不改 relay 流程、不改 RelayInfo |
| 不碰计费 | 禁止 | 本表不记 quota、不查 logs、不做任何计费运算；token 数仅来自响应 usage 解析 |
| 开关不进后台 | 强制 | `CONVERSATION_LOG_ENABLED` 走环境变量（`common.GetEnvOrDefaultBool`），不进 OptionMap |
| 存储仅 ClickHouse | 强制 | `conversation_turns` 仅落 ClickHouse 日志库（`LOG_SQL_DSN`），不落 SQLite/MySQL/PostgreSQL；开启 `CONVERSATION_LOG_ENABLED` 时必须配置 ClickHouse，未配置时功能不生效 |

### 3.2 性能要求

| 指标 | 要求 | 说明 |
|------|------|------|
| 开关关闭开销 | 近似 0 | 直接 `c.Next()`，不包装 writer、不读 Body |
| 捕获链路附加延迟 | 低（微秒级） | 请求体经 GetBodyStorage 缓存读取、响应体经 buffer 拷贝，均为内存操作，异步写库不阻塞响应 |
| 响应 buffer 上限 | 256KB | 超限截断并置 `truncated` 标记、记录截断字节数；请求 body 同阈值兜底 |
| 异步写库 | 不阻塞请求 | 整体在 `gopool.Go` 异步 goroutine 内，闭包只捕获纯值 |
| 会话缓存命中 | Redis / 进程内 map | 命中即复用 sessionKey 并滚动续期，TTL 30min |

### 3.3 兼容性要求

#### 数据库兼容性
| 依赖 | 版本要求 | 说明 |
|------|---------|------|
| SQLite | — | 不承载 `conversation_turns`（存储仅 ClickHouse） |
| MySQL | — | 不承载 `conversation_turns`（存储仅 ClickHouse） |
| PostgreSQL | — | 不承载 `conversation_turns`（存储仅 ClickHouse） |
| ClickHouse | 项目支持版本 | 手写 DDL：`id Int64 DEFAULT 0`、`ENGINE=MergeTree()`、`PARTITION BY toYYYYMM(toDateTime(created_at))`、`ORDER BY (session_key, created_at, request_id)`、TTL 读 `LOG_CONVERSATION_CLICKHOUSE_TTL_DAYS`（与 `logs` 表的 `LOG_SQL_CLICKHOUSE_TTL_DAYS` 独立） |

#### 代码约束（遵循项目 AGENTS.md）
- `common.Marshal`/`common.Unmarshal` 等包装函数用于消息序列化，业务代码禁止直接调用 `encoding/json`。
- `group` 保留字列名按 `logGroupCol` 方言约定处理。
- 查询拼接一律 `ORDER BY created_at, request_id`（与 logs 表双键排序一致），ClickHouse 建表 `ORDER BY (session_key, created_at, request_id)`。
- `relaykit/` 模块独立性不受影响（本组件全部位于根模块）。

#### 协议与路径白名单（首版范围）
| 协议 | 路径 |
|------|------|
| OpenAI | `/v1/chat/completions`、`/v1/completions`、`/v1/responses`（含 compact） |
| Claude | `/v1/messages` |
| Gemini | `:generateContent`/`:streamGenerateContent`（后缀匹配，覆盖 `/v1beta/models/*` 与 `/v1/models/*` 两个入口） |
| 不覆盖 | `/v1/realtime`（websocket 不经 c.Writer）、转写/TTS/embedding/image/rerank 等非对话路径 |

白名单集中在一处，便于调整。OpenAI/Claude 走精确路径匹配；Gemini 走后缀匹配。

### 3.4 安全要求

| 安全项 | 要求 | 实现方式 |
|--------|------|---------|
| 访问控制 | 查询 API 仅管理员 | `GET /api/conversation/` 与 `GET /api/conversation/:session_key` 挂在管理员路由组 |
| 敏感信息 | token 明文 key 不落库 | 只存 `token_name`，管理员按名称查询，与 logs 表惯例一致 |
| 审计 | 会话详情不泄露无关维度 | 不回传 ip/channel_id/token_id/use_time 等整表字段 |
| 内存安全 | 响应捕获有上限 | 256KB buffer 上限 + `truncated` 标记，避免大响应占用过多内存 |

### 3.5 可靠性要求

| 项 | 要求 | 说明 |
|----|------|------|
| 建表幂等 | 启动迁移 `CREATE TABLE IF NOT EXISTS` | `migrateClickHouseLogDB` 启动时建表，幂等无副作用，配置变更重启即重新对齐 TTL |
| 会话续链 | Redis 状态 | 网关重启不断链（TTL 内续得上），多副本跨实例续上同一会话 |
| 并发首请求 | `RedisSetNX` 原子抢占 | 消除同一会话首批请求并发劈会话窗口 |
| 单实例退化 | 明确标注 | Redis 未配置时退化进程内 map，`common.SysError` 输出「单实例模式」提示 |
| Redis 运行期故障 | 记日志、按新会话回退 | Redis 已配置但运行期连接失败/超时（`redisSetNX`/`RedisGet` 出错）时，捕获链路不中断，本轮按新建会话回退生成 sessionKey，故障期间会话续链失效，`common.SysError` 记录，恢复后自动回到 Redis 模式 |
| 失败请求入库 | 统一记录 | 4xx/5xx 响应同样入库，assistant 侧解析失败记空、usage 失败记 0，缺失维度记零值 |

|---------|---------|------|---------|
| `CONVERSATION_LOG_ENABLED` | 状态 | 功能开关状态 | — |
| 捕获写入失败率 | 计数 | 写库失败次数 / 总捕获次数 | > 0.1% |
| 截断率 | 计数 | 响应超 256KB 被截断的比例 | 关注，长回复语义需知情 |
| 单实例退化 | 日志 | Redis 未配置时的 SysError 输出 | 多副本部署时应告警 |

### 6.3 告警规则

| 告警名称 | 触发条件 | 严重程度 | 处理建议 |
|---------|---------|---------|---------|
| 写库持续失败 | 捕获写入失败率升高 | 中 | 检查 ClickHouse（`LOG_SQL_DSN`）连接与磁盘，确认 `migrateClickHouseLogDB` 启动迁移建表成功（`conversation_turns` 表存在） |
| 单实例退化 | Redis 未配置但多副本部署 | 高 | 配置 Redis，否则会话在多副本下断裂 |
| 截断频发 | truncated 记录占比过高 | 低 | 评估是否调高 256KB buffer 上限 |

### 6.4 故障排查

#### 常见问题

**问题1：开启后没有数据写入**
- 现象：`CONVERSATION_LOG_ENABLED=true` 后查询无记录
- 原因：路径不在白名单内（如 /v1/embeddings），或 middleware 未挂在目标路由分组，或未配置 ClickHouse 日志库（LOG_SQL_DSN），或开关未真正生效
- 解决：核对白名单路径、挂载位置；确认已配置 LOG_SQL_DSN 指向 ClickHouse；确认请求走 `/v1/chat/completions` 等文本对话路径

**问题2：流式记录的 completion_tokens 为 0**
- 现象：流式请求 completion_tokens=0
- 原因：客户端未带 `stream_options.include_usage`，末个 chunk 无 usage
- 解决：属协议限制，查询侧对 completion_tokens=0 的流式记录知情即可，客户端侧可加 `stream_options.include_usage`

**问题3：多副本部署下会话断裂**
- 现象：同一对话被切成多段
- 原因：Redis 未配置，退化进程内 map，跨实例不共享会话缓存
- 解决：配置 Redis；`SysError` 日志会标注单实例模式

**问题4：对话被误并或断链**
- 现象：启发式边界与预期不符
- 原因：客户端裁剪/压缩 history 会断链（会话切成多段，段内正确）；客户端不带 history 无法关联；同 token 并发极端相似对话可能误并
- 解决：属协议无状态 + 客户端不可改的客观限制，会话状态落 Redis 后网关重启不再断链（TTL 内续得上）
