## 1. 设计总览

### 1.1 接口清单

本功能新增 **1 个接口**。前端表单所需的分组列表、模型选择器数据复用现有查询接口（见 1.3），渠道列表查询本身无改动。

| 序号 | 方法 | 路径 | 用途 | 权限 | 需求追溯 |
|-----|------|------|------|------|---------|
| 1 | POST | `/api/channel/batch/update` | 批量统一编辑勾选渠道的可编辑字段（空即跳过语义） | ChannelWrite | 4.2.3 保存批量编辑、4.2.4 规则1/3/4/5 |

### 1.2 设计说明

**方法选择**：批量编辑为变更操作，按项目约定使用 POST。本仓库现有渠道批量操作的路由惯例为 POST + 语义路径（`/api/channel/status/batch`、`/api/channel/batch/tag`），本接口路径 `/api/channel/batch/update` 与之保持一致。

**空即跳过语义**（4.2.4 规则1）：请求体中所有可编辑字段均为**指针类型且可省略**。字段出现（非 null）即对全部选中渠道统一替换为所填值；字段省略或为 null 即跳过，保持各渠道原值。任何字段都不提供"清空"语义（模型重定向传空字符串 `""` 视为已填写但值为空串，与单个编辑口径一致，校验层拒绝空串，见 2.2.6）。

**事务全成全败**（4.2.4 规则3）：后端在单个数据库事务内逐渠道执行"更新 channel 行 + 重建 abilities 路由索引"，任一渠道失败即整体回滚，失败响应携带触发回滚的渠道 ID 与原因（串行执行遇首个失败即回滚，数组恒为单元素）。

**排除字段**：name、key、type、base_url、openai_organization、other、setting、settings、param_override、header_override、status_code_mapping、multi_key_mode、key_mode、proxy、other_info、channel_info 均不在请求体中接受（对应 4.2.2 D 区排除清单）。后端请求 DTO 仅声明白名单字段，其余字段即使传入也不解析，天然实现排除。

### 1.3 复用的现有接口（本功能不改动）

| 接口 | 用途 | 需求追溯 |
|------|------|---------|
| GET `/api/group/` | 批量编辑抽屉"分组"下拉多选的选项来源 | 4.2.5 分组为下拉多选，选项来自系统分组列表 |
| GET `/api/channel/models` | 模型选择器候选模型来源 | 4.2.5 模型列表支持从模型选择器多选 |
| GET `/api/channel/` | 成功后刷新渠道列表 | 4.2.4 规则6 |

## 2. 接口详细设计

### 2.1 批量编辑渠道

**接口路径：** `POST /api/channel/batch/update`

**需求追溯：** 4.1.3 打开批量编辑（提交侧）、4.2.3 保存批量编辑、4.2.4 规则1（空即跳过）、规则2（类型无关字段）、规则3（事务全成全败）、规则4（abilities 与独占索引同步）、规则5（审计日志）、4.3.3 确认执行

**权限：** `middleware.AdminAuth()` + `middleware.RequirePermission(authz.ChannelWrite)`

无权限时 HTTP 403（`message` 经 `i18n.MsgAuthInsufficientPrivilege` 本地化，中文环境为"无权进行此操作，权限不足"）：

```json
{
  "success": false,
  "message": "<本地化文案>"
}
```

**限流：** 无独立限流（挂载于 `/api/channel` 管理路由组，与现有批量启停、批量设标签同级别）。

**请求参数（`application/json`）：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| ids | integer[] | 是 | 目标渠道 ID 列表，1 ~ 200 条（4.2.4 规则3 上限） |
| group | string | 否 | 分组，逗号分隔串，长度 (0,64]，选项应来自系统分组列表 |
| tag | string | 否 | 标签，长度 (0,191]（上限对齐 channels.tag 列现状 varchar(191)） |
| remark | string | 否 | 备注，长度 (0,255] |
| models | string | 否 | 模型列表，逗号分隔串，单个模型名 ≤255；语义为统一替换，无追加语义 |
| model_mapping | string | 否 | 模型重定向，JSON 对象序列化串 |
| weight | integer | 否 | 权重，0 ~ 4294967295（uint32） |
| priority | integer | 否 | 优先级，int64 范围 |
| test_model | string | 否 | 测试模型，长度 (0,255] |
| auto_ban | integer | 否 | 自动封禁：`1`=启用、`0`=停用；省略即"不变"（三态中的跳过态，4.2.2 C 区） |

字段生效语义：字段**出现且非 null** 即生效（统一替换）；**省略或 null** 即跳过。至少 1 个字段生效，否则返回参数错误。

**请求示例：**

```json
{
  "ids": [1, 2, 3],
  "group": "default,vip",
  "models": "gpt-4o,claude-3-5-sonnet",
  "weight": 10,
  "auto_ban": 1
}
```

**处理流程：**

1. 参数校验（见 2.2）：ids 非空且 ≤200、生效字段数 ≥1、各字段值域与长度校验、model_mapping 为合法 JSON 对象
2. 开启事务，按 ids 查出全部渠道（事务内），逐渠道：
   - 将生效字段写入该渠道（其余字段保持原值）
   - 该渠道涉及路由相关字段（models/group/weight/priority/tag）时重建 abilities（事务内，失败整体回滚）
3. 任一渠道失败 → 整体回滚，返回失败明细（见错误响应）
4. 全部成功 → 提交事务
5. 事务提交后：刷新渠道缓存（`model.InitChannelCache()`）；调用 P2_CHL_001 的按渠道清理能力，对受影响渠道（指本次有路由相关字段 models/group/weight/priority/tag 生效的渠道；全部路由字段均未生效时跳过清理）同批清除反向占用索引条目、最近绑定记录与该渠道仍持有的正向绑定（三批同清，对齐 P2_CHL_001 的 5.2.2 第7条与 5.2.4 规则2），清理失败重试一次，仍失败记服务端错误日志、残留条目随 TTL 收敛，不阻断结果（4.2.4 规则4）
   - **依赖状态**：该能力由 P2_CHL_001 经 service 层导出函数提供，函数名与签名待其落地后回填；P2_CHL_001 当前 `dev_exec` 为 in_progress，service 层尚无按渠道清理的导出函数。本 Feature 的 dev_plan 须将该项列为阻塞前置6. 记录管理员审计日志（4.2.4 规则5）：
   - action：`channel.update_batch`
   - params：`{count, channel_ids, updated_fields, values}`，values 记录各生效字段所填值**全量原文**（不做截断）
   - 兜底模板（auditContentTemplates）：`"Batch updated ${count} channels (fields: ${updated_fields})"`

**成功响应（HTTP 200）：**

```json
{
  "success": true,
  "message": "",
  "data": {
    "count": 3
  }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| count | integer | 实际更新的渠道数量 |

**失败响应（HTTP 200，业务失败）：**

参数校验失败（无生效字段、超上限、值非法等）：

```json
{
  "success": false,
  "message": "批量编辑至少需要填写一个字段"
}
```

事务执行失败（全成全败，全部渠道回滚到编辑前状态；4.2.4 规则3）：

```json
{
  "success": false,
  "message": "批量编辑失败，已全部回滚",
  "data": {
    "failed": [
      { "id": 2, "reason": "更新 abilities 失败: ..." }
    ]
  }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| data.failed[].id | integer | 触发回滚的失败渠道 ID |
| data.failed[].reason | string | 该渠道失败原因 |

失败响应携带 `data.failed`（串行执行遇首个失败即回滚，数组恒为单元素，保留数组形态便于后续扩展），前端在抽屉内展示（4.2.4 规则3），已填内容与勾选状态由前端保留。

### 2.2 参数校验规则

校验顺序：结构解析 → ids 边界 → 生效字段数 → 逐字段校验。任一步失败即返回，不触达数据库。

#### 2.2.1 ids

| 规则 | 错误消息 | 依据 |
|------|---------|------|
| 非空数组，元素为正整数 | 参数错误 | 4.1.2 至少勾选 1 条 |
| `len(ids) <= 200` | 单次批量编辑上限 200 条，请分批操作 | 4.2.4 规则3 |

#### 2.2.2 group

| 规则 | 错误消息 | 依据 |
|------|---------|------|
| 长度 (0,64]（去除首尾空白后非空才视为生效） | 分组长度不能超过 64 字符 | 4.2.2 A 区 |
| 格式：逗号分隔串，去除空白段后各段非空 | 分组格式错误 | 4.2.2 A 区 |

选项来源为系统分组列表，由前端下拉多选保证；后端不做存在性强校验（与单个编辑口径一致，分组可在渠道保存先于分组配置创建）。

#### 2.2.3 tag / remark / test_model

| 字段 | 规则 | 错误消息 | 依据 |
|------|------|---------|------|
| tag | 长度 (0,191] | 标签长度不能超过 191 字符 | 4.2.2 A 区（对齐 channels.tag 列现状） |
| remark | 长度 (0,255] | 备注长度不能超过 255 字符 | 4.2.2 A 区 |
| test_model | 长度 (0,255]，去除空白后非空才视为生效 | 测试模型长度不能超过 255 字符 | 4.2.2 C 区 |

三者均为去除首尾空白后空串 → 视为未填写（跳过），与前端表单留空语义对齐。

#### 2.2.4 models

| 规则 | 错误消息 | 依据 |
|------|---------|------|
| 逗号分隔串，去除空白段后各段非空 | 模型列表格式错误 | 4.2.2 B 区 |
| 单个模型名 ≤255 字符 | 模型名称过长: {name} | 与 validateChannel 添加路径同口径（批量编辑自主执行，防护 abilities.model 列长 varchar(255)） |
| 整体语义为统一替换 | - | 4.2.2 B 区（无追加语义） |

去除空白段后为空 → 视为未填写。

#### 2.2.5 weight / priority

| 字段 | 规则 | 错误消息 | 依据 |
|------|------|---------|------|
| weight | 整数，0 ≤ v ≤ 4294967295 | 权重必须在 0-4294967295 之间 | 4.2.2 C 区（uint32，与 Channel.Weight *uint 一致） |
| priority | 整数，int64 范围（-9223372036854775808 ~ 9223372036854775807） | 优先级超出范围 | 4.2.2 C 区 |

DTO 以 `*int` / `*int64` 精确解析，禁止经 float64 中转：priority 声明的 int64 全域在 2^53 以上无法被 float64 精确表示，经浮点中转会静默改变取值。非整数输入（如 `10.5`）在解析阶段即被拒绝；weight 拒绝负数。

#### 2.2.6 model_mapping

| 规则 | 错误消息 | 依据 |
|------|---------|------|
| 已填写时须为合法 JSON **对象**（`common.Unmarshal` 到 map，顶层非对象/数组/数组字面量均拒绝） | 模型重定向必须是合法的 JSON 对象 | 4.2.2 B 区 |
| 去除首尾空白后为空串 → 拒绝（清空不属于批量编辑语义，走单个编辑） | 模型重定向不能为空（如需清空请在单个编辑中操作） | 4.2.4 规则1（无清空语义） |

#### 2.2.7 auto_ban

| 规则 | 错误消息 | 依据 |
|------|---------|------|
| 已填写时取值仅 `0` 或 `1`；省略/null 即"不变" | 自动封禁取值错误 | 4.2.2 C 区（三态：不变/启用/停用） |

存储映射：`1` → `AutoBan=1`（启用），`0` → `AutoBan=0`（停用），与 Channel.AutoBan *int 既有编码一致（`GetAutoBan()` 判 `*v == 1`）。

#### 2.2.8 生效字段数

| 规则 | 错误消息 | 依据 |
|------|---------|------|
| 去重后的生效字段数 ≥ 1 | 批量编辑至少需要填写一个字段 | 4.3.4 规则1（无生效字段拦截，后端兜底；前端在保存时先行拦截） |

#### 2.2.9 未知字段

请求体中 D 区排除字段及其他未知字段**不解析、不报错**（白名单 DTO），从协议层面保证排除字段不可通过本接口修改。

### 2.3 错误响应汇总

| 场景 | HTTP 状态码 | 响应形态 | 说明 |
|------|-----------|---------|------|
| 认证失败 | 401 | `{"success":false,"code":"AUTH_*","message":"..."}` | AdminAuth 会话/JWT 校验 |
| 权限不足 | 403 | `{"success":false,"message":"<本地化文案>"}` | RequirePermission(ChannelWrite)，message 经 i18n.MsgAuthInsufficientPrivilege |
| 参数校验失败 | 200 | `{"success":false,"message":"<具体原因>"}` | 2.2 各规则 |
| 事务失败（已回滚） | 200 | `{"success":false,"message":"...","data":{"failed":[...]}}` | 全成全败，携带失败明细 |
| 服务端异常 | 200 | `{"success":false,"message":"<错误信息>"}` | 兜底 |

本项目管理接口主流程错误统一 HTTP 200 + `success:false` + `message`，无独立错误码字段（规则文件 §2.2），错误场景由 message 区分，上表已覆盖全部场景。

**响应构造说明：** 参数校验失败与服务端异常走既有 `common.ApiError` / `common.ApiErrorI18n`（仅 `success`/`message`）。事务失败响应需额外携带 `data.failed` 失败明细（4.2.4 规则3），`common.ApiError` 不产出 `data` 字段，该分支须由 handler 直接 `c.JSON` 构造，形态与上表一致，不引入新的响应约定。

### 2.4 并发与幂等说明

| 关注点 | 设计 |
|--------|------|
| 防重复提交 | 前端保存按钮 loading 至响应返回（4.2.3）；后端无幂等键，重复提交等同两次批量编辑，操作本身幂等（同一份表单重复提交结果一致） |
| 与单个编辑并发 | 渠道行更新走 GORM `Updates(map[string]any)`（按 id 定位，map 形式不做零值过滤，保证 weight/priority/auto_ban 的 0 值写入，见数据库模型设计 3.1），abilities 重建在事务内 delete+insert；事务保证单次批量内部一致 |
| 与独占绑定并发 | 事务提交后按渠道清理反向占用索引、最近绑定记录与该渠道仍持有的正向绑定（三批同清），失败重试一次后仍失败走 TTL 收敛，与 P2_CHL_001 的 5.2.2 第7条、5.2.4 规则2 语义一致 |
| 渠道不存在 | ids 中不存在的渠道跳过（`Updates` 零行影响不报错）；`count` 为实际更新数，与现有 `channel.delete_batch` 返回实际删除数的口径一致 |

## 3. 安全说明

| 项 | 说明 |
|----|------|
| 认证 | 管理后台 JWT/Session（AdminAuth），非 API Key 路径 |
| 授权 | Casbin 权限点 `channel:write`；表单仅含非敏感字段，无 ChannelSensitiveWrite 判定（4.2.2 D 区 + 2.2 权限说明） |
| 敏感数据 | 请求与响应均不携带渠道密钥；审计 values 记录所填值原文（用户已填写的表单值，非密钥） |
| 输入验证 | 白名单 DTO + 逐字段长度/格式/范围校验（2.2）；ids 上限 200 防大事务 |
| 审计 | 成功提交记 `channel.update_batch` 审计日志，含渠道数量、ID 列表、生效字段与所填值全量 |

## 4. 需求覆盖追溯

| 需求点 | 接口/设计落点 |
|--------|--------------|
| 4.1.3 打开批量编辑（按钮入口、权限） | 前端交互；权限由 POST /api/channel/batch/update 的 RequirePermission 保证 |
| 4.2.2 A/B/C 区可编辑字段 | 请求体 10 个可选字段（group/tag/remark/models/model_mapping/weight/priority/test_model/auto_ban + ids） |
| 4.2.2 D 区排除字段 | 白名单 DTO 不解析（2.2.9） |
| 4.2.4 规则1 空即跳过 | 指针字段省略/null 跳过（1.2、2.1） |
| 4.2.4 规则2 类型无关字段 | 请求体不含类型相关字段；混合类型渠道可提交 |
| 4.2.4 规则3 事务全成全败 + 200 上限 | 处理流程 2-4 步；校验 2.2.1；失败响应 data.failed |
| 4.2.4 规则4 abilities + 独占索引 | 处理流程 2、5 步 |
| 4.2.4 规则5 审计日志 | 处理流程 6 步（channel.update_batch） |
| 4.2.4 规则6 成功后清理 | data.count 驱动前端"已更新 N 条渠道"提示与列表刷新 |
| 4.3.4 规则1 无生效字段拦截 | 校验 2.2.8 |
| 2.2 页面访问权限（ChannelWrite） | 接口权限（403 响应） |
