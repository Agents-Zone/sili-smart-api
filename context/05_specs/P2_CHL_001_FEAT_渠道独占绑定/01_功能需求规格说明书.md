# 功能需求规格说明书

## 1. 概述

### 1.1 功能背景

现有渠道亲和性功能（channel_affinity_setting）按亲和键（如 token_id、prompt_cache_key、metadata.user_id）将请求粘住同一渠道，用于提升上游 prompt cache 命中率。但它是纯软亲和：任何亲和键都可能命中任何渠道，多个不同 api_key 的请求会被路由到同一个渠道账号，导致该上游账号被多人共用，显著提高渠道被封控的风险。

同时存在亲和稳定性缺陷：同一亲和键并发首次请求（cache miss）时各自选路并互相覆盖缓存，请求失败重试切换渠道后也会覆盖原绑定，造成同一 api_key 在多台机器上跑时被路由到多个渠道（绑定漂移）。

### 1.2 本功能业务目标

1. 渠道独占：启用独占的亲和规则下，同一渠道同一时刻仅允许被一个亲和键独占绑定；满载（无空闲渠道）时才允许复用，复用时按最少绑定数优先分摊，降低单渠道账号的多人共用压力
2. 绑定稳定：消除绑定漂移，同一亲和键并发首次绑定时先到先得、原子生效；TTL 到期重绑时优先绑回原渠道；除渠道失败切换外，绑定期间不换渠道
3. 可审计：满载复用降级事件在消费日志管理员信息中留痕，独占/复用状态可在现有设置区统计行中观测
4. 兼容现状：亲和命中路径行为不变，未启用独占的规则保持现有软亲和行为

## 5. 非页面功能详细说明

### 5.1 独占绑定选路引擎

#### 5.1.1 功能概述

**触发方式：** 事件监听（每次中转请求的渠道分发阶段）
**触发时机：** 中转请求进入渠道分发，亲和规则命中且缓存 miss 时执行绑定决策；亲和命中时沿用现有行为
**功能职责：** 在渠道选定时刻按独占语义完成绑定决策与原子占位，治理绑定漂移

#### 5.1.2 处理流程

1. 亲和命中（正向缓存存在该亲和键的绑定）：行为不变，直接校验渠道可用性后使用
2. 亲和 miss 且该规则启用独占绑定：
   - 依据现有选路获得当前分组+模型下的可用渠道候选集合
   - 读取反向占用索引，筛出未被其它亲和键绑定的空闲渠道（本键既有绑定视为空闲）
   - 存在空闲渠道：在空闲渠道集合内选定。若本键的最近绑定记录（见 5.1.3）仍存在、记录的原绑定渠道仍可用且空闲，优先绑回原渠道；否则沿用现有选路策略在空闲集合内选定
   - 无空闲渠道（满载）：降级复用，按最少绑定数优先选定渠道（绑定数并列时沿用现有选路策略），绑定标记为复用，触发 5.3 降级审计
   - 绑定写入必须原子且先到先得：同一亲和键并发首次绑定时，仅第一个完成占位写入的请求生效，其余请求读取胜者占位结果并使用同一渠道（单实例进程内串行化，多实例部署时经 Redis 原子操作实现）
3. 亲和 miss 且该规则未启用独占绑定：沿用现有选路与软亲和行为，但绑定结果同步登记反向占用索引（见 5.2）
4. 请求执行完成后沿用现有回写逻辑（成功回写绑定）；请求失败且切换渠道成功时，绑定迁移到新渠道，反向占用索引同步从旧渠道移除该键、登记到新渠道。失败切换为紧急路径，迁入新渠道时豁免独占判定（新渠道即使已被其它键占用也直接迁入，按复用处理并计入统计口径），迁入失败或无候选渠道时沿用现有重试语义；请求最终失败且未发生成功切换时，回滚本次占位（正向绑定、反向占用索引与最近绑定记录同批清除），下次请求重新选路，避免失败请求的占位把亲和键钉在失败渠道上直至 TTL 到期；亲和判定渠道不可用时的清缓存行为沿用现有 keep_on_channel_disabled 语义，清除时同步清理反向占用索引与最近绑定记录

#### 5.1.3 涉及数据

| 数据项 | 数据来源 | 数据用途 | 说明 |
|-------|---------|---------|------|
| 亲和键值 | 请求上下文（KeySources 提取） | 绑定与独占判定主体 | 独占判定按亲和键值去重；规则亲和键配置为 token_id 时等价于按 api_key 判定 |
| 正向亲和缓存 | 现有 HybridCache | 键→渠道绑定 | 结构与 TTL 沿用现状 |
| 反向占用索引 | 本功能新增（与正向缓存同存储体系） | 渠道→绑定键集合 | 见 5.2 |
| 最近绑定记录 | 本功能新增（与正向缓存同存储体系） | TTL 过期重绑时优先绑回原渠道的依据 | 键→渠道 + 绑定时间戳，随正向绑定写入时同步写入；记录使用独立配置 last_bind_ttl_seconds，默认 604800 秒（7 天），有效保留期取配置值与绑定 TTL 两倍中的较大者；从最近一次绑定写入或成功续期开始计算，到期自动清除；管理员清空缓存与独占开关切换保存时同步清除（见 5.2.2） |
| 可用渠道候选 | 现有渠道选路 | 独占判定的渠道范围 | 沿用现有分组+模型过滤 |

#### 5.1.4 业务规则

- **规则1：** 独占判定以渠道为单位全局生效（跨规则）：渠道的反向占用索引中已存在其它亲和键绑定时，该渠道对启用独占的规则为非空闲
- **规则2：** 绑定决策与占位写入原子化，先到先得；除渠道失败切换（现有 SwitchOnSuccess 语义）外，绑定有效期内同一亲和键不换渠道
- **规则3：** 满载判定仅看可用候选渠道：候选渠道全部被占用才降级复用，复用选最少绑定数优先
- **规则4：** TTL 到期重绑优先绑回原渠道，原渠道不可用或被占用时走正常独占选路；历史记录本身不占用渠道，全部候选满载时仍按最少绑定数分配
- **规则5（独占粒度边界）：** 独占判定粒度跟随规则的亲和键配置。亲和键为 token_id 时等价于按 api_key 独占，与"每渠道仅被一个 api_key 绑定"的验收口径一致；亲和键为 prompt_cache_key、metadata.user_id 等非 token_id 类型时，同一 api_key 的请求可产生多个亲和键、各自独占不同渠道，极端情况下单个 api_key 可能占用多个甚至全部渠道。此边界属于设计内的行为，通过 4.1.5 的开启前重点提醒向管理员显式暴露，由管理员自行评估亲和键类型与独占开关的组合是否适用

#### 5.1.5 异常处理

| 异常场景 | 处理方式 | 错误提示/日志 |
|---------|---------|--------------|
| 反向占用索引读写失败 | 请求不阻塞，降级为现有软亲和行为，按独占未生效处理；降级请求在 gin context 置存储降级标记，请求成功回写时跳过绑定固化（随机选路结果不写入正向缓存与占用索引），该键下次请求重新走完整独占决策（v1.9） | 服务端错误日志（SysError），含渠道与键指纹 |
| 原子占位竞争失败 | 读取胜者绑定结果并使用同一渠道 | 无 |
| 占位回滚失败（终态失败时清除占位出错） | 记录错误日志后放行，残留条目随 TTL 自然过期 | 服务端错误日志（SysError），含渠道与键指纹 |
| 降级复用发生 | 允许复用并记录审计 | 见 5.3 |

#### 5.1.6 与其他功能的关联

- **上游依赖：** 现有渠道亲和性服务（service/channel_affinity.go）、渠道分发（middleware/distributor.go）、渠道选路（CacheGetRandomSatisfiedChannel）
- **下游影响：** 所有启用独占规则的请求路由结果、消费日志管理员信息

### 5.2 反向占用索引管理

#### 5.2.1 功能概述

**触发方式：** 事件监听（随绑定写入/清除/过期联动）+ 下游操作调用（渠道配置变更）
**触发时机：** 任何亲和规则产生绑定回写、绑定迁移、绑定清除，管理员清空缓存、独占开关切换保存，或渠道的路由相关配置被下游操作（如渠道批量编辑 P2_CHL_002）变更时
**功能职责：** 维护渠道→绑定键集合的反向索引，为独占判定、最少绑定数选路、统计指标提供数据

#### 5.2.2 处理流程

1. 绑定写入：正向缓存写入键→渠道的同时，向该渠道的索引条目登记该键，过期时间与正向绑定同 TTL；同步写入该键的最近绑定记录（键→渠道 + 绑定时间戳，见 5.1.3）
2. 绑定迁移：失败切换渠道时，从旧渠道条目移除该键并登记到新渠道条目，最近绑定记录同步更新为新渠道
3. 自然过期：条目随 TTL 过期自动失效，无需主动清理；最近绑定记录使用独立保留期，默认 7 天且至少为绑定 TTL 的两倍，到期自动清除
4. 主动清空：管理员清空全部亲和缓存、按规则清空、独占开关切换保存时，对应的反向索引条目、最近绑定记录与正向缓存同批清空
5. 重启恢复：索引随缓存体系存续（Redis 部署时持久，单实例内存部署时重建，绑定关系随请求自动重建）
6. 多实例部署边界：多实例部署且缓存体系运行于内存模式（未启用 Redis）时，反向占用索引与原子占位在实例间不可见，独占判定与先到先得语义不保证，行为退化为现有软亲和。该边界属于已知限制，通过部署文档（README 部署章节）说明，不增加运行时检测
7. 渠道配置变更清理：渠道的路由相关配置（models/group/weight/priority/tag）被下游操作（渠道批量编辑 P2_CHL_002 等）变更后，对该渠道同批清除反向索引条目、最近绑定记录与该渠道仍持有的正向绑定（三批同清，规则2 口径）；清理失败重试一次，仍失败记错误日志，残留随 TTL 收敛（5.2.5），不阻断下游操作结果

#### 5.2.3 涉及数据

| 数据项 | 数据来源 | 数据用途 | 说明 |
|-------|---------|---------|------|
| 渠道→键集合索引 | 绑定事件写入 | 独占判定、最少绑定数、统计 | 与正向亲和缓存同一 HybridCache 体系（Redis 优先、内存回退），独立命名空间 |
| 键指纹 | 亲和键哈希（沿用现有 affinityFingerprint） | 索引内标识键 | 索引不存原始键值，存指纹，避免敏感信息扩散 |

#### 5.2.4 业务规则

- **规则1：** 所有亲和规则（无论是否启用独占）的绑定均登记反向占用索引；仅启用独占的规则在绑定时检查索引执行独占判定
- **规则2：** 索引条目 TTL 与对应正向绑定一致；最近绑定记录 TTL 由 last_bind_ttl_seconds 独立配置（允许 1 至 31536000 秒，默认 604800 秒），实际值至少为正向绑定的两个周期；清空操作必须正向缓存、反向索引与最近绑定记录同批执行

#### 5.2.5 异常处理

| 异常场景 | 处理方式 | 错误提示/日志 |
|---------|---------|--------------|
| 索引清空失败 | 重试一次，仍失败则记录错误日志，部分失败不反映在接口响应中（沿用现有清缓存反馈形态，残留随 TTL 过期兜底） | 服务端错误日志 |
| 渠道配置变更清理失败 | 重试一次，仍失败记错误日志，不阻断调用方（渠道批量编辑）结果，残留随 TTL 收敛 | 服务端错误日志 |

#### 5.2.6 与其他功能的关联

- **上游依赖：** 5.1 选路引擎、现有缓存清空接口
- **下游影响：** 4.2 统计指标、5.1 独占判定、渠道批量编辑（P2_CHL_002，渠道路由配置变更后按渠道清理）

### 5.3 降级审计与统计指标

#### 5.3.1 功能概述

**触发方式：** 事件监听（降级发生时）+ API 调用（统计查询）
**触发时机：** 满载复用降级发生时记录审计；设置页加载/刷新时返回指标

#### 5.3.2 处理流程

## 6. 数据状态定义

### 6.1 数据状态

状态主体：某亲和键在反向占用索引中与某渠道的绑定关系。

| 状态名称 | 状态说明 | 可转换到的状态 |
|---------|---------|--------------|
| 未绑定 | 键无有效绑定（无正向缓存条目） | 独占绑定、复用共享 |
| 独占绑定 | 键持有该渠道当前唯一绑定 | 复用共享（渠道维度）、已释放、独占绑定（换渠道） |
| 复用共享 | 键绑定到同时被其它键绑定的渠道（满载降级产生） | 独占绑定（渠道维度回归唯一）、已释放、独占绑定（换渠道） |
| 已释放 | 绑定因 TTL 到期、缓存清除或渠道不可用清除 | 未绑定 |

### 6.2 状态转换规则

| 当前状态 | 可转换到的状态 | 转换条件 | 转换触发方式 |
|---------|------------|---------|-------------|
| 未绑定 | 独占绑定 | 存在空闲渠道，原子占位成功（先到先得） | 系统自动（选路） |
| 未绑定 | 复用共享 | 无空闲渠道（满载），最少绑定数优先降级 | 系统自动（选路） |
| 独占绑定 | 复用共享 | 其它键满载降级绑入同一渠道（渠道键数大于 1） | 系统自动（选路） |
| 复用共享 | 独占绑定 | 同渠道其它键绑定全部释放，渠道键数回归 1 | 系统自动（TTL 过期） |
| 独占绑定 / 复用共享 | 独占绑定（换渠道） | 请求失败切换渠道成功，绑定迁移 | 系统自动（失败重试） |
| 独占绑定 / 复用共享 | 已释放 | TTL 到期；管理员清空缓存；独占开关切换保存；渠道亲和判定不可用且 keep_on_channel_disabled=false | 系统自动 / 管理员操作 |
| 已释放 | 独占绑定 | TTL 到期后重绑：经未绑定状态发起一次新的独占选路，原渠道仍可用且空闲时优先绑回原渠道（依据最近绑定记录） | 系统自动（选路） |

## 8. 附录

### 8.1 术语表

| 术语 | 定义 | 说明 |
|------|------|------|
| 亲和键 | 亲和规则 KeySources 从请求中提取的绑定主体（如 token_id、prompt_cache_key、metadata.user_id） | 独占判定按亲和键值去重；独占粒度跟随亲和键类型，见 5.1.4 规则5 |
| 独占绑定 | 渠道当前仅被一个亲和键绑定的状态 | 启用独占的规则追求的目标状态 |
| 满载复用（降级） | 可用候选渠道全部被占用时，新亲和键按最少绑定数优先绑定到已占用渠道 | 唯一允许渠道多人共用的场景 |
| 反向占用索引 | 渠道→绑定键集合的运行时索引 | 与正向亲和缓存同存储体系、同 TTL |
| 最近绑定记录 | 键→最近一次绑定渠道 + 绑定时间戳的运行时记录 | TTL 过期重绑时优先绑回原渠道的依据，保留两个 TTL 周期 |
| 先到先得原子绑定 | 同一亲和键并发首次绑定时首个完成占位者生效 | 治理并发 miss 漂移 |
| 绑定漂移 | 同一亲和键在绑定有效期内被路由到不同渠道的现象 | 本功能要消除的缺陷（渠道失败切换除外） |
| 键指纹 | 亲和键经哈希截断得到的非可逆标识（SHA1 前 16 位 hex，偏离记录 D5） | 反向索引与审计中标识键，避免扩散敏感键值 |

| D1 | 独占选路在空闲集合与满载并列层的渠道选定采用集内均匀随机，未复用现有选路的渠道权重加权随机 | 候选集导出接口仅返回渠道 ID、无权重维度；仅影响选定分布均匀性，独占/复用/先到先得语义不变 | 5.1.2 第2条（沿用现有选路策略的表述） |
| D2 | 独占开关切换清空时，若旧规则未启用 include_rule_name 且键构成无法回放出可区分前缀，退化为正向缓存、反向占用索引、最近绑定记录整体清空（并记服务端日志） | 该形态下无法定位该规则专属的键范围；清空方向为多清而非少清，保证旧语义数据不残留；默认内置规则与前端新建规则均启用 include_rule_name，触发面窄 | 4.1.4 规则1、5.2.2 第4条（该规则的） |
| D3 | （v1.9 已修复，记录历史偏离）跨键并发首绑的占位串行化曾以亲和键为粒度（分段锁按亲和键哈希、Redis SetNX 按正向键），不同亲和键并发 miss 时各自读取占用索引的瞬间视图可能同时判定同一渠道空闲并各自占位，该渠道键数变为 2（静默复用，无降级标记）。生产观察证实该竞态在多令牌并发开工时高频发生且与「渠道富裕仍多人同占」症状吻合。修复：独占占位改为渠道维度条件占位（内存模式渠道条目分段锁内读-判-写；Redis 模式 occupancyClaimExclusiveScript Lua 脚本原子判定），冲突时决策方从空闲集剔除该渠道重选，直至占位成功或转入满载降级（带标记与计数）。独占模式（Mode=exclusive）的静默双占已消除，满载降级复用仍是认可终态 | 原设计以成本为由接受偶发复用；生产反馈证明其频率与可见性不可接受，条件占位的实现成本经开发验证可接受 | 5.1.2 第2条末、5.1.4 规则2（原子化承诺扩展到跨键场景） |
| D4 | 终态失败回滚不区分亲和 miss 占位与亲和命中：命中路径同样按首次占位渠道标记回滚三处数据；同键后续请求已成功建立新绑定后，先前请求才终态失败的并发窗口内可能误清该新绑定 | 命中与 miss 的占位三处数据同构，统一回滚避免失败渠道被钉住至 TTL（v1.2 回滚语义的动机）；误清窗口极窄且下次请求重新选路即恢复（无数据损坏，仅稳定性瞬时回退） | 5.1.2 第1条（行为不变）、5.1.2 第4条末（回滚范围） |
| D5 | 键指纹由原亲和缓存的 SHA1 前 8 位 hex 加长为前 16 位 hex（64bit 截断） | 8 位 hex（32bit）在默认 10 万键容量下生日碰撞近乎必然（约 6.5 万键即 50%），碰撞会跨键误判占用与误删成员；64bit 截断在同容量下碰撞概率可忽略。指纹不进入持久化数据，仅存运行时缓存与审计标记，加长对存量无迁移成本 | 8.1 键指纹、5.2.3 |
| D6 | 移除路径在 Redis 模式下曾为裸 GET→SET 读改写（v1.7 已修复，记录历史偏离）：移除回写会覆盖并发登记/占位脚本刚追加的成员，成员丢失使渠道占用被低估、独占误判空闲，新键与既有持有键真实同占一个渠道且无降级标记。与 D3 同源（check-then-act 竞态），但发生在移除侧：D3 修复原子化了登记与条件占位两条写路径，漏掉了移除这第三条。修复：occupancyRemoveScript Lua 脚本原子完成"读条目→删成员→空则 DEL / 按剩余 TTL 写回"，登记/占位/移除三条写路径在 Redis 模式下全部原子 | 并发移除与登记交错发生于失败重试迁移、终态失败回滚、管理员清空等场景，与其它键的登记并发是生产常态；04 文档 v1.3 曾断言"移除幂等且方向收敛、无并发正确性风险"，并发守恒回路（20 移除对 20 登记丢 5 成员）证伪了该断言 | 5.2.2 第2条（绑定迁移的索引同步原子性） |
